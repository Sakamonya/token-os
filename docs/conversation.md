“Win的启动逻辑”可以从两个层面来理解：**操作系统本身的启动流程**，以及**应用程序如何被启动**（包括开机自启和用户手动打开）。

### 🖥️ 层面一：操作系统如何启动

Windows 的系统启动是一个从硬件到软件、从内核到用户界面的分层过程，主要经历以下几个关键阶段[reference:0]：

1. **固件初始化（BIOS/UEFI）**：计算机通电后，**BIOS或UEFI**进行硬件自检（POST）并初始化硬件。随后，它根据启动顺序找到硬盘等设备上的**引导加载程序**并加载到内存。
2. **Windows Boot Manager**：这是启动管理器，会**显示引导菜单**（如果安装了多个系统），让你选择要启动的操作系统，然后加载对应的**OS Loader**。
3. **Windows OS Loader**：`winload.exe`（或UEFI下的`winload.efi`）负责**加载启动所需的关键驱动程序**，为内核启动做好准备。
4. **内核初始化**：Windows内核`ntoskrnl.exe`被加载，它初始化内存管理、设备驱动等核心系统组件。
5. **会话管理器启动**：内核启动**会话管理器（`smss.exe`）**，它负责建立系统环境、启动用户模式驱动和系统服务，并最终加载`winlogon.exe`（登录程序）。
6. **用户登录与桌面**：`winlogon.exe`显示登录界面，验证用户身份。登录后，系统加载**用户配置文件**并启动`explorer.exe`（资源管理器），最终呈现**桌面、任务栏和图标**。

> **补充**：在支持UEFI的现代计算机上，**安全启动（Secure Boot）** 会在加载引导程序前验证其数字签名，以防恶意软件篡改启动过程。

### ⚙️ 层面二：应用程序如何被启动

应用程序的启动逻辑，关键在于**启动时机**和**由谁触发**。

**开机自启的机制**
这些机制决定了程序在系统启动的哪个阶段被拉起，核心区别在于**是否依赖用户登录**以及**触发时机**。

*   **系统服务（Services）**：**在用户登录前**，由系统自动启动，适合需要后台常驻、无界面的核心程序（如杀毒软件、驱动服务）[reference:3]。
*   **计划任务（Scheduled Tasks）**：最灵活。触发器可设为“**计算机启动时**”（无需登录）或“**用户登录时**”，适合需要特定权限或延迟启动的任务。
*   **注册表 Run 键**：最经典的方式，位于`HKLM`（对所有用户生效）或`HKCU`（仅当前用户）下。**用户登录后**执行，适合普通桌面程序。
*   **启动文件夹（Startup Folder）**：将快捷方式放入“启动”文件夹，**用户登录后**执行，操作最简单，但同样依赖用户登录。

**关键的进程创建流程（以双击 .exe 为例）**
当你手动打开一个程序时，核心是 `CreateProcess` 函数触发的内核级操作[reference:5]：
1.  **映像映射**：系统将`.exe`文件从磁盘映射到内存，并解析其PE文件头。
2.  **创建内核对象**：创建进程内核对象（PCB）和独立的虚拟地址空间。
3.  **加载与初始化**：将代码和数据加载到地址空间，建立初始的栈和堆，并创建**主线程**。
4.  **入口点执行**：主线程开始执行，加载必要的DLL并完成初始化，最终调用程序的**入口点函数**，程序正式运行。

总的来说，Windows的启动逻辑是一个严谨的“接力”过程：从固件到Boot Manager，再到内核和会话管理器，最后交付给用户登录和桌面环境。而应用程序的启动，则是在这个接力过程的不同时间点，通过服务、计划任务、注册表或用户交互等方式被触发和创建的。

DOS（**D**isk **O**perating **S**ystem，磁盘操作系统）是早期个人计算机上的一类操作系统，也是Windows系统出现之前，PC兼容机市场中最主流的操作系统。

### 🖥️ 核心特征：一个“单纯”的系统
和你刚了解的现代Windows启动逻辑相比，DOS的设计非常原始和直接：

*   **单用户、单任务**：它一次只能为一个用户服务，并且**同一时间只能运行一个程序**。想同时听歌和写文档？在纯DOS环境下是做不到的。
*   **命令行界面**：与Windows的图形化桌面不同，DOS**完全依赖键盘输入命令**来操作。比如要查看文件，需要手动输入 `dir` 并回车，而不是用鼠标点击[reference:2]。
*   **核心是管理磁盘**：顾名思义，它的主要职责就是管理磁盘上的文件（创建、复制、删除等），这是当时个人电脑最核心的需求[reference:3]。

### 📜 历史地位：Windows的“基石”
DOS与Windows的关系，远比“前后辈”要深刻：

*   **Windows的起点**：早期的Windows，如**Windows 1.0到3.x**，本质上只是运行在DOS之上的一个“图形应用程序”，并非独立的操作系统。电脑启动时，依然是**先加载DOS，再由用户手动输入命令启动Windows**。[reference:5]
*   **关键的过渡**：**Windows 95**是第一个将DOS“吸收”进来的系统，它让用户开机后直接进入图形界面。但Windows 95/98/Me的内核深处，依然有DOS的痕迹，直到2000年后基于NT架构的Windows（如XP）才彻底摆脱了对DOS的依赖。[reference:6][reference:7]

### 💡 现代的“遗迹”
纯DOS虽然早已退役，但它的操作逻辑依然留存至今：

*   **命令提示符（cmd）**：你在Windows里打开的“命令提示符”窗口，就是DOS命令行界面的现代延续。许多基础命令（如 `cd`、`dir`）都一脉相承[reference:8]。
*   **FreeDOS**：一个开源的DOS兼容系统，至今仍在维护，主要用于运行老旧软件或刷新主板BIOS等特殊场景。

DOS就像是个人电脑的“童年时代”，它用最直接、纯粹的方式教会了计算机如何管理文件，并为后来Windows的辉煌图形界面奠定了不可或缺的基石。

## 一、两种“agent 直接驱动硬件”的解释

1. **Agent-centric bare-metal OS（可行）**
   - 裸机上第一个复杂程序就是 Agent 内核。
   - 它拥有全部硬件：CPU 特权级、页表、中断、MMIO、DMA。
   - LLM 通过工具调用请求“读寄存器/写寄存器/订阅中断”。
   - 策略引擎、权限表、看门狗、事务日志在 LLM 之外，保证安全。

2. **LLM 直接跑在裸机上并逐条决策硬件（不现实）**
   - 中断上下文不能调 LLM。
   - 延迟、token 成本、非确定性、幻觉会导致设备状态机崩溃。
   - 只能作为 QEMU 里的实验：LLM 生成驱动代码，热加载到沙箱执行。

建议做 1，把 2 作为受限实验。

## 二、裸机 Agent OS 的启动逻辑

以 RISC-V QEMU virt 为例，比 x86_64 简单得多：

```
上电
→ 固件/OpenSBI
→ bootloader 加载 agent-kernel 到内存
→ 设置栈、清 BSS、建立初始页表

→ 建立 trap/中断向量
→ 初始化 Agent 运行时：能力表、工具注册表、日志、任务队列
→ 启动 Agent 主循环

```

x86_64 则多出：实模式/保护模式/长模式切换、GDT/IDT、APIC、ACPI、PCIe 枚举等，起步更难。

## 三、Agent 如何“直接读写寄存器”

在裸机内核里，寄存器访问就是几类原语：

- **MMIO**：把物理地址映射到虚拟地址，用 `volatile` 指针读写。
- **Port I/O**：x86 的 `in/out` 指令。
- **MSR**：x86 的 `rdmsr/wrmsr`。
- **CSR**：RISC-V 的 `csrr/csrw`。
- **DMA**：配置设备寄存器，让设备直接读写内存，需 IOMMU/MPU 保护。
- **中断**：注册 IRQ handler；handler 只做最小记录，唤醒 agent 任务，不调 LLM。

Rust 裸机示例：UART MMIO 写寄存器

```rust
const UART0: usize = 0x1000_0000;

unsafe fn uart_write_byte(b: u8) {
    let reg = UART0 as *mut u8;
    core::ptr::write_volatile(reg, b);
}
```

Agent 工具注册表示例：

```rust
Tool {
    name: "mmio_write_u8",
    schema: { addr: u64, value: u8 },
    capability: Cap::MmioWrite(range),
    handler: |args| unsafe {
        core::ptr::write_volatile(args.addr as *mut u8, args.value);
        Ok(())
    }
}
```

LLM 只能调用 `mmio_write_u8`，不能直接执行任意指针。运行时负责：
- 地址是否在允许范围；
- 设备是否已授权；
- 是否可能影响关键寄存器；
- 是否需人工审批；
- 写前日志、写后校验、失败回滚。

## 四、必须有的安全与可靠性机制

裸机 agent 有硬件权限后，风险是“一行错误配置就死机/烧设备”。必须有：

1. **能力系统**：按设备/地址区间/中断号授权，最小权限。
2. **MMU/MPU/IOMMU**：限制 agent 可访问的物理地址和 DMA 范围。
3. **看门狗**：agent 卡死自动复位，保留崩溃日志。
4. **中断与 LLM 解耦**：中断 handler 只记录事件；LLM 在主循环处理。
5. **事务日志**：关键寄存器写前记录旧值，支持回滚。
6. **模拟器优先**：先在 QEMU 跑通，再上真实硬件。
7. **人工审批**：电源、时钟、PCIe 配置等高风险操作需确认。
8. **确定性反射层**：常见设备驱动用状态机/规则，不让 LLM 每次从零推理。

### Cortex-A 还是 Cortex-M：先做对选择

你要的“寄存器级 agent 内核”，应该选 **ARM Cortex-A（ARMv8-A / AArch64）**，而不是 Cortex-M。

Cortex-M 的向量表、异常模型更简单，适合极简固件，但它通常没有 MMU，内存保护靠 MPU，隔离能力有限，难以支撑多任务 agent 或子 agent 的地址空间隔离。Cortex-A 有完整的**异常级别（EL0–EL3）**、MMU 和 **TrustZone**，天然适合做“agent 内核 + 隔离沙箱”的骨架[reference:1]。

### 相比 RISC-V 的额外复杂度与额外能力

**启动链更复杂**：ARM Cortex-A 上电后通常从 **EL3（Secure Monitor）** 开始，需要配置 `SCR_EL3`、设置 `VBAR_EL1`、建立页表、从 EL3 逐级降到 EL1，然后才能开 MMU 运行你的内核[reference:2]。RISC-V 从 M-mode 到 S-mode 的路径直白得多。这是 ARM 的入门门槛。

**但换来了硬件级隔离能力**：**TrustZone** 可以把“agent 内核”和“不可信工具/子 agent”放进 **Secure world** 与 **Normal world** 两个硬件隔离域。你可以让 agent 核心运行在 Secure world，拥有对关键寄存器和内存的独占访问；而 Normal world 里的子任务即使失控，也无法触及核心硬件状态[reference:3]。这是 RISC-V 的 PMP 在裸机场景下较难达到的隔离粒度。

### 中断与寄存器访问：ARM 有成熟的基础设施

- **寄存器访问**：和 RISC-V 一样是 MMIO，用 `volatile` 指针或 Rust 的 `safe-mmio` 类型系统封装即可，ARM 生态里还有 **SVD 文件**可以自动生成寄存器定义[reference:4]。
- **中断控制器**：ARM 的 **GIC**（Generic Interrupt Controller）有成熟的裸机 Rust 驱动，支持 GICv2/v3，`no_std` 可用，可以直接集成进你的 agent 内核的工具层。
- **MSR 访问**：Kanzashi 已经实现了 `msr_amd64.go` 和 `reg_arm64.s`，为 agent 提供了读写**特定于模型的寄存器（MSR）**的汇编原语[reference:6]。

### 建议的起步路线（ARM 版）

**平台**：QEMU `virt` + `cortex-a72` 或 `cortex-a53`，用 `qemu-system-aarch64 -machine virt -cpu cortex-a72 -m 128M -nographic` 跑你的裸机 ELF。

**最小内核骨架**：
1. **linker script**：加载地址 `0x40000000`，划分 `.text.boot`、`.text`、`.rodata`、`.data`、`.bss`、栈和页表空间[reference:9]。
2. **启动汇编**：从 EL3 开始，设置栈，读 `CurrentEL`，配置 `SCR_EL3`（`RW=1, NS=1`），设置 `VBAR_EL1`，建立恒等映射页表，`ERET` 到 EL1，开 MMU，通过 PL011 UART（`0x09000000`）输出第一行字符串[reference:10]。
3. **GIC 初始化**：集成 `arm-gic-driver`，初始化 Distributor 和当前 CPU 接口，使能时钟中断。
4. **Agent 运行时**：工具表注册 `mmio_read/write`、`msr_read/write`、`gic_subscribe`；能力表限定地址范围和中断号；日志记录每次寄存器访问。
5. **接入 LLM**：先用 QEMU 的 semihosting 或虚拟网卡把工具调用 JSON 送出去，LLM 侧返回决策，运行时校验后执行。

### 为什么不同板子的固件会影响“第一步写法”

不是因为你必须手写，而是因为**第一行代码的运行环境由固件决定**。具体差异包括：

1. **入口地址不同**：树莓派 `kernel8.img` 通常加载到 `0x80000`；QEMU `virt` 常见加载到 `0x40000000`；i.MX8 由 TF-A/U-Boot 决定。
2. **异常级别不同**：上电后可能停在 EL3、EL2 或 EL1。你要不要自己降级、配 `SCR_EL3`、设 `VBAR_EL1`，取决于固件已经把环境准备到哪一步。
3. **固件留下的接口不同**：PSCI、U-Boot 的 bootm、TF-A 的 BL31、OpenSBI 的 SBI 调用，决定你怎么关机、复位、启核。
4. **串口和中断控制器不同**：PL011 地址、GICv2/v3、定时器频率、设备树有没有传进来，都影响最早期的调试输出和中断初始化。
5. **内存布局和安全状态不同**：TrustZone 是否已配置、DDR 是否已初始化、页表是否已存在，决定你的 linker script 和 MMU 初始化怎么写。
6. **加载格式不同**：ELF、raw binary、FIT image、U-Boot script，决定上位机 agent 怎么打包和烧录。

所以“第一步写法”受固件影响，这是事实；但**不该由人肉记忆**，应该变成**板级 manifest + 上位机 agent 的 codegen 和验证闭环**。

### Token 流的真实需求

云端 LLM 吐 token 的速率大概是 10–100 token/s，每个 token 几字节到几十字节。这本质是**稀疏的离散事件**，不是字节流。所以本地硬件需要的不是大带宽，而是：

- **中断/事件唤醒**：token 到达要能叫醒 agent 内核，而不是轮询大缓冲区。
- **消息边界**：每个 token 或每批 token 是一个有边界、有序号、可校验的消息。
- **低延迟**：agent 决策等不起几百毫秒的协议栈抖动。
- **背压**：本地处理不过来时，网关要能暂停或降级。
- **可审计/可重放**：token 丢失或重复会直接影响决策，必须有序号和日志。

### 底层通道选项，按“底层程度”排

1. **UART 串口 + 自定义帧协议**  
   最底层、最简单。帧格式：`magic + seq + len + payload + crc`。上位机网关把云端 token 转发到串口，目标内核收中断、解帧、入事件队列。带宽完全够，适合 QEMU 和早期真实板。缺点：单链路、无寻址、速率低但够用。

2. **网卡 + 极简链路，不跑完整协议栈**  
   网卡本身非常合适：它是 **DMA 设备 + 中断源**。你可以只用 raw Ethernet frame 或 UDP 单包，甚至自定义 EtherType，一个 token 一个包或小批量打包。目标内核写极简 NIC 驱动：DMA 环形接收队列 + 中断处理 + 零拷贝取包。带宽大不是缺点，你可以限速、批量聚合、降低中断频率。**这才是“token 落到本地硬件”最标准的底层手段。**

3. **virtio-net / virtio-serial / ivshmem（QEMU/VM 场景）**  
   如果本地硬件是 QEMU 或带虚拟化通道的板子，virtqueue 就是现成的低延迟、中断驱动、零拷贝通道。上位机把 token 写入 virtqueue，目标内核收中断、取描述符。比真实网卡简单，适合先跑通闭环。

4. **PCIe DMA + MSI-X**  
   真实板子上最底层：上位机或加速卡通过 PCIe BAR 写 token 到目标内存，触发 MSI-X 中断。适合高性能、低延迟，但复杂度最高，需要 IOMMU 保护。

5. **USB CDC / raw bulk**  
   介于串口和网卡之间，适合没有以太网的板子。

6. **JTAG/SWD semihosting**  
   只适合 bring-up 调试，不适合运行时 token 通道。

```

- 网卡 agent：决定 DMA 描述符怎么写、中断什么时候触发、环形队列深度
- 内核 agent：决定 token 进入哪个任务队列、唤醒谁、是否合并
- 决策 agent：消费 token，产生工具调用

**每一层都是 agent，每一层都在做语义到物理的映射。** 这就是“token 活在电路上”。

### 但必须区分两种 agent

如果每一层都调 LLM，延迟和可靠性会崩。正确形态是：

- **确定性微 agent**：物理层、链路层、中断处理。状态机 + 规则 + 能力表，**LLM 不在实时路径上**。
- **半确定性 agent**：传输层、会话层。规则为主，LLM 处理异常、拥塞、重路由。
- **LLM 主导 agent**：语义层、决策层。token 的真正消费者。
- **元 agent**：生成、验证、替换下层 agent。这是你说的“每一层交给 agent 处理”的真正含义——**agent 管理 agent**。

### “token 活在电路上”的工程表达

一个 token 到达本地硬件时，应该触发一条确定的物理事件链：

```
云端 token
→ 网关生成带序号的 token 消息
→ 链路层 agent 决定帧格式和发送时机
→ 网卡 DMA 写入环形队列
→ MSI-X 中断触发
→ 中断 agent 取描述符、校验、入有界队列
→ 调度 agent 根据 token 优先级唤醒任务
→ 决策 agent 消费 token，产生下一轮工具调用
```

每一步都是 agent 在决策，但**实时路径上的 agent 必须是确定性的**。LLM 只出现在“这一层该怎么配置”“异常怎么恢复”“策略怎么调整”这些非实时决策点。

### 分层 agent 的关键设计

1. **每层 agent 有明确的能力边界**：物理层 agent 只能碰 DMA 描述符和中断寄存器；链路层 agent 只能碰帧缓冲；决策 agent 只能调工具。能力表按层隔离。
2. **每层 agent 可观测、可回滚**：每个 token 的路径有 trace，某层 agent 出错可以降级到确定性后备逻辑。
3. **层间契约是消息，不是函数调用**：token 消息带序号、时间戳、优先级、校验，层与层之间是异步事件，不是同步阻塞。
4. **元 agent 负责生成和验证下层 agent**：这是“从 0 写系统”的真正含义——不是人写每一层，是上位机元 agent 生成、测试、部署每一层的确定性逻辑和 LLM 策略。
5. **背压是全局的**：token 流稀疏，但突发时每层 agent 都要能暂停上游、降级、丢弃低优先级 token，而不是缓冲区爆掉。

### 为什么这不是 OS

OS 的核心是“资源抽象 + 隔离 + 调度”。你的系统核心是 **“语义到物理的连续换能”**。进程、文件、系统调用这些概念在这里不是必需的——token 是唯一的一等公民，agent 是每层的解释器，硬件是 token 的最终落点。

更准确的名字可能是：**Token-Native Hardware Fabric**，或者 **Semantic Signal Plane**。它不是管理硬件，而是让语义直接驱动硬件。

### 最难的部分

不是“让 token 上电路”，而是 **让每层 agent 可验证、可组合、可回滚**。一旦某层 agent 的决策不确定，整个 token 流的时序就不可预测。所以：

- 实时层必须确定性，LLM 只能做离线策略生成和异常诊断。
- 每层 agent 要有形式化的输入输出契约。
- 元 agent 要有能力做“层替换”的回归测试。
- 全链路 trace 是刚需，没有它就无法定位是哪层 agent 把 token 弄丢了。

### 一、上下文的最小单位：事件，不是 token

每个上下文条目是一条**事件记录**，至少包含：

```
event_id        全局单调递增序号
parent_id       因果父事件（这条上下文由谁触发）
timestamp       物理时钟
type            USER_INPUT | MODEL_TOKEN | TOOL_CALL | TOOL_RESULT
                | REG_READ | REG_WRITE | IRQ | CHECKPOINT | SNAPSHOT
payload         内容（token 文本、工具参数、寄存器地址+旧值+新值）
phys_effect     物理副作用摘要（无副作用则空）
window_digest   该事件在云端窗口中的压缩表示
```

**关键：每条事件先落盘，再进入任何处理路径。** 这叫 write-ahead context。云端吐出 token 的那一刻，本地先 append 到日志，再解析、再执行。崩溃时日志就是真相。

### 二、冷启动：不是从零开始，是状态差异比对

冷启动分三种，对应三种策略：

1. **正常上电**：硬件状态干净。加载硬盘上最后一个 `CHECKPOINT`，读取当前寄存器/内存/队列状态，生成一条 `BOOT_DIFF` 事件。如果差异在预期内，继续；否则进安全模式。
2. **崩溃后重启**：日志尾部可能有不完整事件。扫描最后一条 `CHECKPOINT` 之后的所有事件，找出 `phys_effect` 非空但缺少 `TOOL_RESULT` 的条目——这些是"悬空副作用"。进恢复模式：逐条检查寄存器实际值是否匹配预期，能回滚则回滚，不能则标记人工介入。
3. **硬盘迁移/换板**：加载日志，读取新板状态，生成 `BOOT_DIFF`。如果硬件型号不同，差异会很大，强制进只读诊断模式，agent 先感知硬件，再决定是否继续。

冷启动的输出不是"上下文窗口"，而是一条**启动事件**，它成为后续所有事件的因果根。

### 三、上下文进入：窗口是投影，不是存储

云端有窗口上限。本地维护三层：

```
L0 活跃窗口     ← 直接发给云端，最近 N 条事件的压缩投影
L1 摘要层       ← 老事件的语义摘要 + 关键寄存器最终状态
L2 完整日志     ← 硬盘上 append-only，永不丢弃
```

组装窗口时：

1. 从 L2 取最近事件，按因果链排序。
2. 超过阈值时，把最老的连续段压成一条 `SUMMARY` 事件，写入 L1。
3. `SUMMARY` 必须保留：任务目标、关键决策、寄存器最终状态、未完成副作用、待验证假设。
4. 窗口 = L1 最近摘要 + L0 最近原始事件。

**压缩不是丢信息，是换表示。** 原始事件永远在 L2，需要时可回放、可审计、可重放给云端。

### 四、上下文退出：token 落地即留痕

云端 token 到达本地后的路径：

```
NIC/串口中断
→ 中断 agent：收帧、校验、append 原始帧到日志
→ 链路 agent：去重、排序、append 解析后 token
→ 会话 agent：更新活跃窗口，识别工具调用边界
→ 决策 agent：生成 TOOL_CALL 事件
→ 能力检查：地址范围、权限、是否高危
→ 执行：寄存器读写 / DMA / 中断订阅
→ append TOOL_RESULT（含实际读回值）
→ 若结果影响硬件状态，append CHECKPOINT
```

每一步都是先写日志再动作。**寄存器写操作必须记录旧值、新值、地址、调用者事件 ID。** 这就是你说的"什么事都得留痕"。

### 五、上下文与寄存器操作的耦合点

云端吐出的 token 可能直接变成寄存器操作，所以上下文不是"参考"，是**执行前提**。规则：

1. **任何 `REG_WRITE` 必须挂在某个 `TOOL_CALL` 下，`TOOL_CALL` 必须挂在某个 `MODEL_TOKEN` 下。** 因果链断了，拒绝执行。
2. **写前快照**：高危寄存器写之前，append 一条 `CHECKPOINT`，记录相关寄存器组当前值。
3. **写后验证**：读回寄存器，append `TOOL_RESULT`。读回不符，append `ANOMALY`，触发回滚或安全模式。
4. **上下文版本**：每次窗口投影带一个 `context_version`。如果执行时发现硬件状态与投影中的假设不符，拒绝执行，重新组装窗口。

### 六、硬盘布局

```
/ctx/log/000001.wal       追加写，固定大小段文件

### 八、最难的三个点

- TLS 1.3 握手（X25519 密钥交换、证书链校验）
- AES-GCM 加密和 SHA-256
- 一个可信的随机数源（裸机没有 `/dev/urandom`，得从硬件时钟抖动里榨熵）
- 上面还有 HTTP/1.1 分块传输 + 逐 token 推送的流式解析

这不是"几千行"的量级，是一个密码学库加一个协议栈。**你现在做这个，会在第 300 行卡住，而不是在第 3000 行。**

所以真正的问题不是"怎么连上去"，而是：

> **TLS 必须发生在这条链路的某一端。你要决定的只有一件事：放在裸机里做，还是放在中继里做。**

这是二选一，没有第三条路。

## 三条路，按"最短"排

### 路径一：串口当字符设备（半天能通）

```
内核 ──串口帧──> 上位机小脚本 ──HTTPS──> api.deepseek.com
     <──token帧──
```

上位机那个脚本只有几十行：收到一帧就转成一个 HTTPS 请求，把返回的流原样切帧写回串口。**它不解析语义、不存对话、不知道你在干什么。**

- 优点：今天就能看到 token 从云端流进裸机内核
- 缺点：走的是串口，不是网卡，跟将来真板子的形态不一样

### 路径二：网卡 + 极简 UDP（几天）

```
内核 ──virtio-net──> QEMU 内建 NAT ──UDP──> 上位机中继 ──HTTPS──> 云端
```

QEMU 的 `-netdev user` 自带 DHCP 和 NAT，你**不用自己写网络地址转换**。内核侧只需要：virtio-net 驱动（收发环形队列 + 中断）+ 极简 IP/UDP（不写 TCP，不写 TLS）。中继把 UDP 帧翻译成 HTTPS。

- 优点：这才是你之前说的"token 当消息、网卡当消息设备"的真正落地形态，也是将来上真板子的同一条路
- 缺点：virtio-net 驱动是真正的工作量，环形队列 + 中断 + 描述符，得啃一两天

### 路径三：裸机自己跑 TLS（几个月，现在别碰）

技术上成立，但会把你从"做系统的人"变成"写密码学库的人"，而且做完之前整个项目停摆。等真板子跑起来了再考虑，那时候可能要的是另一个东西：**在板子旁边放一个协处理器/小 MCU 专门做 TLS**，而不是让主核干这个。

## API key 放哪

这是你问的那个点的答案：**放内核镜像里的只读区**。

每次请求时，内核把这串 key 连同请求一起通过串口/网卡发出去，中继用完即弃、不落盘。这样：

- key 物理上在本地设备里，不在云端、不在上位机的配置文件里
- 上位机真的只是一段电线——它连"记住你是谁"都做不到
- 换一台上位机，key 还是只有一个副本，在你手上

## 架构上最关键的一句话

**别把它当成"接一个 API"，要把它当成"注册一个 token 设备"。**

内核里应该长这样：

```c
// 上层代码只认这个，永远不用改
struct token_device {
    int  (*submit)(const char *request);   // 把上下文打包发出去
    int  (*poll)(struct token_event *out); // 取一个到达的 token / 事件
};
```

底层实现先接串口，将来换网卡、换真板子，**上层一行都不用动**。这就回答了"通过什么方式接入"——方式是可替换的，接口是不变的。这也是自持系统该有的样子：设备可以换，内核的骨架不动。

## 有一个矛盾要你拍板

路径一和路径二里，token 的明文会**短暂经过**上位机中继。你之前明确说过"上下文不能存在上位机"，那这里要区分两件事：

- **经过**：中继看到一个请求的明文，转手就忘——**不持有状态**
- **存储**：中继留着对话历史、会话 id、缓存——**这才是你反对的**

我的判断是：路径一/二的中继属于前者，可以接受，而且这是唯一现实的起点。但如果你要求"连一瞬间的明文都不经过第三方进程"，那唯一的路就是路径三，代价是几个月。

这个选择得你自己定，因为它关系到你整个项目的原则纯度。

## 顺带踩出来的三个坑（都写进 README 了）

1. **QEMU virt 的 UART1 中断号是 40，不是 34**（`irqmap[VIRT_UART1] = 8`，34 是 RTC）。我按常规猜的 34，结果中断永远不来、FIFO 里明明有数据——查 QEMU 源码才逮住。
2. **`-mstrict-align` 必须有**。MMU 关着时内存按 Device 属性访问，clang 生成一条未对齐的半字存储，直接对齐异常死机。
3. **不能把整条 token 流灌进 16 字节的 FIFO**。中转一开始裸写，内核只收到 35% 就断流了。现在中转按 2 毫秒一帧节流，才做到零丢包。

## 最重要的发现：我不是在造"小号 DSH"，是要补一个缺掉的概念

我把 DSH 的包全翻了一遍（300 多个），agent 本体其实只有八个机制。其中最关键的是一条我之前**完全没有**的东西：

> **DSH 把「日志」和「表面」分开了。留在盘上 ≠ 发给模型。**

具体是这样：压缩**不删事件**。它写三条标记把一段区间"遮蔽"（shadowed），然后在模型看得见的表面插入一条摘要。

```
日志（永久）  [请求] [助手1] [工具调用] [工具结果] [助手2] ...
                    └────── 被遮蔽 ──────┘
表面（模型）  [系统提示] [摘要] [最近 8 轮原文]
```

对比我们的内核：只有 `ctx[]` 一个缓冲区，往里堆字节。**有日志，没有表面。** 所以我们的"压缩"只能是删，而 DSH 的压缩是改投影——可回滚、审计完整、摘要失败也不崩。

`dsh-compaction-basic` 里还有两条硬规则，可以直接抄：**保留最近一段原文**（不全文压缩）、**绝不拆开 tool_call/tool_result 对**（拆开模型会精神错乱）。

## 第三个发现：裸机上有人想过同样的事

搜到一份 [Agent-on-Metal](https://github.com/SuperInstance/fm-research-archive/blob/main/AGENT-ON-METAL-ARCHITECTURE.md) 文档，给 Jetson 设计了三种形态：全裸机、**硬件分区（Jailhouse/TrustZone，正好是我们的 AVF 阶段）**、分布式。它强调的三点和我们判断一致：裸机的价值是确定性；agent 直接当驱动能省掉 `驱动→/dev→read()` 的往返；**不能让 LLM 站在中断路径上**。

## 建议的三步

**M1 · 让内核执行一次工具调用**（不含循环）——请求带两个工具 `read_reg`、`write_reg`，解析 `tool_calls`，执行，停下。验收标准就是屏幕上出现模型让它写的那个字符。

**M2 · 加上循环**——`finish_reason == tool_calls` 就执行再请求，`stop` 才结束，加步数上限防失控。验收标准：模型让它写 "Hi"，屏幕上真的出现 "Hi"，日志里有完整因果链。

**M3 · 压缩 + 冷启动**——surface 指针 + 水位触发摘要 + 遮蔽区间；重启后能说出"我之前在干什么"。

## 几个必须现在定的取舍

| 问题 | 我的建议 |
|---|---|
| JSON 解析器写多大 | 只认我们自己的 schema，字符串扫描，**不做通用解析**（bug 面太大，裸机没兜底） |
| 摘要谁写 | 云端（多一次请求，约 0.001 元） |
| 工具在哪执行 | 内核里直接写寄存器——这是项目意义所在 |
| token 计数 | 中转把 `usage` 用控制帧回传（内核没分词器，数不准） |
| 中断里干什么 | 只收字节记账，不动摇 |

后来它还用 `define_tool` **改写**了自己造的 `hello`，把一个方框和 "Agent" 拼在一起。**内核里没有编译器，但有一个几十行的解释器**——把 `u:X`（打印）、`w:地址,值`（写寄存器）、`d:毫秒`（延时）拼的小脚本当成新工具注册、覆盖、调用。这就是"自我扩展"在这个尺度下的样子。

## 架构（完全照 DSH 的骨架）

| DSH | 这里 |
|---|---|
| session 事件日志 | `log_buf[1500]`，append-only，**永不删** |
| surface 投影 | `surface_start` 指针，模型只看窗口 |
| token-meter | 表面字节 vs 2000 预算 |
| tools 注册表 | 6 个内建 + 12 槽自定义 |
| agent-loop step | `IDLE → WAIT_MODEL → 执行 → IDLE` |

## 顺手踩出四个真坑

1. **把重活放进中断** — 我在 ISR 里执行工具、打印、延时，串口 FIFO 溢出，下一帧直接丢。改成"中断只把一帧拷进作业槽，主循环处理"。**讽刺的是这正是我自己定下的规矩，然后我自己违反了。**
2. **帧头魔数撞车** — `A5 5A` 会出现在中文 JSON 载荷里，中转的"找魔数重同步"误判，整帧丢掉。改成状态机解析。
3. **一次灌整帧** — 4 KB 请求直接写进 16 字节 FIFO，丢 90%。中转改成 6 字节/毫秒慢慢喂。
4. **QEMU chardev 会卡死** — 偶尔停在"等前台开口"，中断再也不来，看着像死机。主循环兜底抽一次 FIFO 就解开。

前三个是设计错误，第四个是模拟器的脾气。这四个都记进了 [README.md](token-os/README.md)。
