token-os · 项目说明

让 token 活在电路上

一台没有操作系统的机器，靠云端吐出的 token 自己活着。

我不是在写一个"能操作硬件的 AI 助手"。
我是在写一台机器，它的心跳、它的记忆、它的决定，全都从一串 token 里长出来。

01一句话说清我在干什么

普通人用 AI：人 → 聊天框 → 云端 → 屏幕上出现字。人停在屏幕后面，机器只是显示。

我在做的事：云端 → 一串 token → 一条自己定义的线 → 一台裸机内核 → 直接写硬件寄存器。中间没有安卓、没有 Linux、没有浏览器、没有对话窗口。token 到达的那一刻，它就是一段会动的电信号，不是一段被显示的文本。

02它不是这些东西

常见误解实际情况
又一个聊天机器人没有聊天界面。输出是串口上的字节和寄存器里的电平。
树莓派跑个 Linux 再调 API没有 Linux。第一条执行的指令是我写的几十行汇编。
把模型塞进小设备模型永远在云端。本地只有一个内核，负责"接住"它的输出。
让 AI 直接控制硬件AI 只能请求工具。真正碰寄存器的是确定性代码，有权限、有日志、可回滚。

03分层：每一层都是"换能器"

传统网络栈的分层是封装/解封装：加头、剥头，语义只在最顶层出现。这里的每一层不是封装，而是把一个语义单元翻译成当前物理层该有的形态。

云端模型
无状态推理。不保存我的会话，只做一次前向计算，吐 token。
↓
链路帧
我自己定义帧格式：magic + 长度 + 序号 + 载荷 + 校验。上位机只负责搬运，不解释。
↓
中断
一个字节到达 → 硬件敲门 → 内核被叫醒。token 是事件，不是流。
↓
事件队列
中断只记一笔就走，重活留给主循环。满了会丢，丢了要计数。
↓
上下文状态机
因果日志、裁剪策略、冷启动恢复。主副本永远在本机。
↓
工具层 / 寄存器
写前记录旧值，写后读回校验。每一笔都可追溯、可回滚。

这里的"每一层交给 agent 处理"，指的是元 agent 生成并验证每层的确定性逻辑，而不是让大模型站在中断里逐条决策——那会把时序搞崩。

04已经能跑的证据

当前跑在一台软件模拟的 ARM 电脑里（QEMU，虚拟板子 virt，CPU cortex-a72）。这台"假电脑"上电后，执行的第一条指令就是我写的启动汇编。

$ make && make run =========================================== token-os v2 / 定时器中断驱动 =========================================== [init] 向量表已装载 [init] GIC 中断控制器就绪 [init] EL1 物理定时器已上弦，周期 1 秒 [init] 硬件计数器频率 = 62500000 Hz [init] 开中断，进入事件循环 HEARTBEAT 1 HEARTBEAT 2 HEARTBEAT 3

这已经不是"程序在跑"，而是系统在活着。三个证据：

① 它真的在睡

空转 6 秒，只消耗了 0.083 秒 CPU（约 1.4%）。没事干的时候它执行 wfi 把核心挂起，等硬件来敲。之前那种轮询写法，会死死占满一个核心。

# 6 秒实际耗时 vs 消耗的 CPU 时间 real=6.023 user=0.044 sys=0.039

② 中断真的会叫醒它

心跳不是"自己问时间到了吗"，是硬件定时器每秒敲门一次，内核被叫醒之后才动。

③ 看门狗真的会叫

我做了一个自测版，让主循环故意卡死 8 秒：

HEARTBEAT 3 [自测] 主循环故意卡死 8 秒，看门狗应该报警... !! 看门狗报警：主循环 5 秒没有响应 !! [自测] 卡死结束，主循环恢复 HEARTBEAT 4 (队列里有一条看门狗事件 —— 主循环恢复后才被处理，这就是积压)

注意那句报警是从中断里打出来的，不是主循环打的——因为主循环这时候已经死了。这就是"报警必须走独立路径"的实感。

这一条链现在是真的通了：云端 → 帧 → 串口中断 → 本地上下文 → 内核自己决定续下一轮。全程没有我参与，也没有人点它。

十分钟暴露出的真问题

上下文缓冲区在 170 秒就满了。64 KiB 装不下三分钟的输出，之后每 5 秒仍然在收 token，但只能记账、不能再存。

这不是 bug，是设计缺口：一台只会"往里塞"的机器迟早会满。真实系统需要滚动窗口 + 摘要压缩 + 定期落盘——正好就是我一开始说的那套"上下文管理"。它现在不是一个抽象话题了，它有了一个具体的时间戳：170 秒。

成本：约 17.4 万个输出 token 加 10 万左右输入，一块多钱。

05b它已经在自己造工具了

2026-11-17 上午，第二次十分钟：内核里跑的不再是"心跳"，是一个有工具、有记忆、会自己续命的 agent。

十分钟自动运行的实测
指标值
模型请求582 次

上下文压缩184 次（摘要 + 遮蔽，日志一条不删）
帧校验失败0
云端错误0

它自己造的工具有 line（横线）、box（方框）、hello、sep（分隔线）、tag（标签）、pulse（呼吸灯）……然后自己调用它们，在串口上真的画了出来：

[新工具] sep = u:-;u:-;u:-;u:-;u:-;u:-;u:-;u:-;u:-;u:- [工具] sep ---------- [新工具] tag = u:[;u:A;u:R;u:M;];u: ;u:o;u:k [工具] tag [ARM] ok

这套工具不是编译器编出来的：内核里有一个几十行的解释器，把 u:X（打印字符）、w:地址,值（写寄存器）、d:毫秒（延时）拼成的小脚本，当成"新工具"注册、覆盖、调用。模型在给自己扩能力，内核负责解释执行。

这一轮踩出来的四个真坑（都修了）
  • 把重活放进中断：执行工具、打印、延时都在 ISR 里，串口 FIFO 溢出，下一帧直接丢。改成"中断只拷一帧进作业槽，主循环处理"。
  • 帧头魔数撞车：A5 5A 会出现在中文 JSON 载荷里，中转"找魔数重同步"会误判。改成状态机解析。
  • 一次灌整帧：4 KB 的帧直接写进 16 字节 FIFO，丢 90%。中转改成 6 字节/1 毫秒慢慢喂。
  • QEMU chardev 会卡死：偶尔停在"等前台开口"，中断不再来。主循环兜底抽一次 FIFO 就解开。

06路线图

阶段一 · 软件模拟跑通中
QEMU 模拟 ARM 电脑。慢，但零风险、可无限重来。验证启动链、中断、队列、看门狗，以及 token 进出的完整链路。
阶段二 · 硬件虚拟化待做
用平板自带的硬件虚拟化（AVF）。速度接近原生，隔离依然存在——内核崩了也伤不到系统本体。
阶段三 · 真实硬件待做
真板子。只有到这一步，"上下文存在这台机器里"才在物理上完全成立。

07五条不能破的原则

上下文主副本在本地
云端只做无状态计算。会话历史、裁剪策略、恢复逻辑，全在本机。上位机断电，本地状态不丢。
key 在机器内部
烧进内核镜像。每次请求由内核自己带上。中转脚本连"记住你是谁"都做不到。
先写日志，再动硬件
任何寄存器写入，写前记旧值，写后读回校验。崩了能查、能回滚、能重放。
中断要短
中断里只记一笔就走。重活留给主循环。中断里跑慢代码，等于自己丢事件。
大模型不在实时路径上
决定"怎么配置、异常怎么恢复"时可以问模型；决定"这一拍该写哪个寄存器"时不能。
先慢后快，一步步来
模拟 → 硬件虚拟化 → 真板子。每一步都要能回滚，每一步都要有日志。

08诚实的边界

现在还做不到的事
  • "机子的硬盘"其实是宿主上的一个文件。逻辑上上下文归内核所有，物理上还要经过宿主。这条边界要等真板子才消失。
  • 中继脚本还不够"自持"。它需要一个不会随会话消失的家，否则就是"有人在旁边举着电线"。
  • 还没有在真板子上验证过时序。模拟器里对的，真硬件上不一定对。
  • 恢复机制还没写。看门狗现在只会喊，不会把系统拉回来。
